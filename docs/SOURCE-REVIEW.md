# 暂停来源的核实与恢复

## 现存来源的增量追踪（0.9.0）

当前按用户选择只追踪现存来源。启动时清点一次 `sessions` 与 `archived_sessions`，随后比较现存文件元数据及已知目录变化：仅枚举变化目录和新子目录，仅对新增/变化 JSONL 读取新增内容；稳定日志不重读，稳定历史目录不每轮递归遍历。刚枚举过的目录会追加一次确认，处理 Windows 同一时间刻度内的目录变更。失败文件保留重试，不会因一次读取失败丢弃待采集任务。

已经消失的路径移出活动集合，不再反复检查或持续报告该来源缺失；历史基线、事件、上传确认、暂停状态及覆盖缺口保留。以后发现原文件或新副本时，重新纳入并按原基线核实，不创建新的重复用量身份。整个采集目录不可用或读权限异常仍会明确报错。

核实窗口的“来源文件变化记录”可查看发现时间、原路径及关联路径。采集器能记录观察到的路径消失、同文件标识迁移、同名压缩文件出现；启动前已消失的来源只能标为“启动时已不存在”。这些事实不能可靠说明由谁、因为什么删除，界面不会编造原因。记录保存在本地 `source_changes`（最多 5000 项，窗口和报告展示最近 50 项）；当前存在性保存在 `source_presence`，不上传这些路径信息。

状态中的 `source_tracking` 提供启动清点次数、本轮目录枚举数、现存文件元数据检查数和变化候选数，便于确认没有每轮重扫全部日志。已关闭告警对应的文件消失后，告警记录转为“移出活动追踪，缺口保留”，不标为缺口已修复。

点击悬浮窗底部“部分来源暂停 · 点击核实”，或右键选择“核实采集来源…”。采集器会检查本机日志和服务器的原基线，显示：

- 每份日志的完整路径、检查点数量、起止时间；
- 是否包含原基线，能否逐条复现本机已保存的事件；
- 与可匹配来源的共同检查点和顺序关系；
- 服务器尚无该流、基线一致、基线不同或连接失败；
- 可恢复条件和当前不能恢复的原因。

## 关闭无法恢复的来源告警

核实窗口顶部的“来源告警”按逻辑来源分组，同一会话的多条缺失路径只算一项。点击“关闭此来源告警…”，填写必需的关闭原因并确认，便可停止当前问题的重复告警。窗口仍显示“部分覆盖”及已关闭数量，不将关闭解释为数据已补齐。

关闭前保存本地 SQLite 备份；关闭时间、原因、执行用户、来源路径、最后已采集时间、保留及待传记录数量和当时来源状态都写入审计。原日志、基线、用量事件、去重身份、上传确认和暂停状态不变；待传记录保留，符合上传条件的继续重试。关闭状态在重启后保留。它只管理来源告警，不能屏蔽网络、认证、队列已满、扫描失败或整个采集目录消失。

“已关闭的告警 / 已确认覆盖缺口”中可以手动“重新打开此告警”。若文件重新出现、内容/元数据改变、发现同来源新副本、采集检查点推进或暂停原因改变，原关闭记录会失效；仍存在的问题重新告警，已消失的问题记为已解决。上传成功本身不会导致重复告警。旧核实报告或文件状态发生变化时，拒绝过时的关闭操作，需重新核实。

记录位于本地账本 `source_alert_closures` 和 `source_alert_audit`，备份位于 `state/source-review-backups/alert-<操作编号>.sqlite3`。核实窗口和 Markdown 报告展示最近 30 项告警操作，完整审计保留在账本中。关闭原因、路径、用户姓名和审计不上传服务器；服务器仍保留原有覆盖不完整的健康原因。

“恢复可证明的重复副本”只处理完整序列相同或短文件为完整文件同序列前缀的情况。文件更大、更新时间更晚、会话 ID 相同都不是自动信任依据。

对于内容不同但其中一份可以复现原基线和全部历史记录的情况，核实窗口允许明确选择“选择此来源并恢复”。确认框列出所选路径及将被排除的其他文件数。其他文件保留在磁盘，但不再参与该流的采集，不把它们的用量混入所选来源。新发现的不同文件仍需要重新核实。

恢复前会重新读取文件并核对指纹、历史事件和服务器状态；文件变化、记录冲突、计数异常、服务器无法核实或基线不同都会拒绝恢复。操作保留原基线、事件 ID、已确认记录及原日志；使用 SQLite 在线备份保存操作前账本，并在同一事务内记录来源选择和排除规则。

核实窗口中的历史记录显示选择时间、所选路径和备份位置。需要改选已排除日志时，先重新核实；如果该流目前没有暂停，请先由维护人员检查后处理，不直接修改数据库。文件移动后若不能验证原基线，仍会暂停并再次提供核实入口。

报告位于当前安装对应的用户状态目录：`state/source-review.json` 与 `state/source-review.md`，审计记录保存在本地账本 `source_review_audit`，操作前备份位于 `state/source-review-backups/`。这些文件含本机路径与用量定位资料，仅在本机使用，不上传阿里云，不宜公开。

## 历史日志被压缩后的处理

原 `.jsonl` 消失但同名 `.jsonl.zst` 存在时，采集器识别为压缩来源，不再笼统报告“未找到采集来源”。它在内存中限量解压，核对会话标识、原基线、全部已保存用量检查点、最后采集位置及文件末尾。仅当核对通过、没有暂停且已保存记录全部获服务器确认时，显示“已同步 · N 个历史来源已压缩”。压缩核实不创建新基线，也不补记未知历史。

核实结果保存在本地账本 `archive_checks`，文件或账本核实依据未变化时直接使用缓存，包括采集器重启后；原 `.jsonl` 再次出现时照常继续采集。待上传记录继续使用原事件 ID 重试，不因日志压缩被删除或标记为已上传。

对于曾扫描但没有建立用量流的文件，核实内容及原采集末尾均一致且没有可采集检查点时，单独列为“无可采集用量的历史来源”。这类文件不算已同步用量，原来的不支持格式或覆盖限制仍会保留，也不会因为压缩而持续报文件丢失。

压缩文件有额外未采集记录、损坏、截断、基线冲突、解压超过 128 MiB 或缺少解码组件时，显示“压缩来源待核实 · 点击查看”。点击底部状态或右键来源核实入口，可查看完整文件路径、具体原因、待传条数及处理建议；“重新核实”会重新读取现存压缩文件。没有任何现存副本的路径移入来源变化记录，不持续报警。未登记压缩历史只列出覆盖缺口，不自动导入。

Python 3.12 的压缩核实组件：使用采集器同一个 Python 执行 `python -m pip install -r client/requirements.txt`。未安装时普通日志采集和已有记录上传仍可运行。此处的文件压缩与模型上下文压缩是两个独立问题；上下文压缩的额外用量仍按现有覆盖限制处理。

命令行也可向正在运行的采集器提交请求：

```powershell
& 'C:\Path\To\python.exe' -m client.source_review
& 'C:\Path\To\python.exe' -m client.source_review --action auto
& 'C:\Path\To\python.exe' -m client.source_review --action close_alert --stream <来源键> --reason '日志已删除且无法找回'
& 'C:\Path\To\python.exe' -m client.source_review --action reopen_alert --stream <来源键>
```

明确选择某份来源时，先检查本地 JSON 报告中的 `stream_id` 和 `source_id`，再使用 `--action resume --stream <stream_id> --source <source_id>`。命令行同样需要新鲜报告，并经过后台相同的核实与审计流程。全局暂停采集期间允许核实；即使来源恢复，也需继续全局采集后才会上传。
